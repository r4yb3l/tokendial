Un modelo de lenguaje solo sabe hacer una cosa: convertir texto en más texto. Todo lo demás que hace tu agente de código, leer un archivo, correr las pruebas, abrir un pull request, consultar Postgres, mover un rectángulo en una herramienta de diseño, ocurre porque un programa alrededor del modelo expone esas acciones como **herramientas**. Hasta finales de 2024 cada asistente inventaba su propia manera de describirlas, así que un conector escrito para uno no servía en el siguiente. El Model Context Protocol, MCP, es el estándar abierto que acabó con eso. Si has añadido un "servidor" a Claude Code, Cursor o VS Code y de pronto el agente veía tus tickets, ya lo has usado.

## El problema que resuelve

Anthropic publicó MCP en noviembre de 2024 y describió la situación que sustituía como un problema "N × M": N asistentes, M fuentes de datos y una integración a medida por cada pareja. La API de *function calling* de OpenAI de 2023 y el marco de plugins de ChatGPT habían resuelto trozos, pero cada uno atado a un fabricante. MCP tomó su forma de algo que los desarrolladores ya conocían, el Language Server Protocol que permite que un plugin de lenguaje funcione en cualquier editor, y la aplicó al contexto: escribe un servidor para tus datos o tu herramienta, y cualquier asistente que hable MCP puede usarlo.

La apuesta salió bien deprisa. OpenAI adoptó el protocolo en marzo de 2025, Google DeepMind lo siguió, y en diciembre de 2025 Anthropic lo donó a la Agentic AI Foundation, bajo la Linux Foundation, fundada junto con Block y OpenAI. A mediados de 2026 se contaban más de 10.000 servidores en producción y los SDK superaban los 97 millones de descargas al mes. La analogía del propio sitio oficial es un puerto USB-C: un conector, cualquier dispositivo.

## Tres participantes

El protocolo nombra tres roles, y los nombres confunden porque "cliente" no eres tú:

- **Host.** La aplicación de IA: Claude Code, Claude Desktop, Cursor, VS Code, ChatGPT. Ejecuta el bucle del modelo y decide cuándo hay que llamar a una herramienta.
- **Cliente.** Un componente dentro del host que mantiene una conexión con un servidor. Conecta Claude Code a un servidor de sistema de archivos y a uno de GitHub y crea dos clientes.
- **Servidor.** Un programa que ofrece contexto y acciones. Puede correr en tu máquina (el servidor de archivos que lanza Claude Desktop) o en la de otro (el servidor alojado de Sentry).

Los servidores locales usan el **transporte stdio**: el host arranca el servidor como proceso hijo y se hablan por la entrada y salida estándar, sin red. Los remotos usan **Streamable HTTP**: HTTP POST para los mensajes, Server-Sent Events opcionales para el streaming, y autenticación HTTP normal, con OAuth recomendado para obtener los tokens. Sea cual sea el transporte, los mensajes son JSON-RPC 2.0, el mismo formato que usan los servidores de lenguaje.

## Qué puede ofrecer un servidor

Lo interesante de MCP es su vocabulario pequeño de **primitivas**, las cosas que un servidor puede exponer:

| Primitiva | Qué es | Ejemplo en un servidor de base de datos |
|---|---|---|
| Herramientas | Funciones que el modelo puede llamar para actuar | `run_query(sql)` |
| Recursos | Datos que el host puede leer al contexto | El esquema de la base de datos |
| Prompts | Plantillas reutilizables para un tipo de interacción | Un ejemplo de consultas bien hechas |

Cada primitiva tiene un método de listado (`tools/list`, `resources/list`, `prompts/list`), así que el host descubre lo disponible al conectarse y no desde un manifiesto fijo. Los servidores también pueden pedir cosas al host: la **elicitación** permite que un servidor solicite más datos o una confirmación al usuario a mitad de una operación. Dos funciones del lado cliente que verás en material antiguo, el *sampling* (un servidor pidiendo una respuesta al modelo del host) y los *roots*, quedaron obsoletas en la revisión de julio de 2026 de la especificación.

Esta es la secuencia cuando escribes "¿por qué falla la prueba del checkout?" en un host conectado a un servidor que corre pruebas:

1. Al conectarse, el host ya pidió al servidor sus herramientas y recibió de cada una el nombre, una descripción en lenguaje natural y el esquema JSON de sus argumentos.
2. Esas descripciones se colocaron **en la ventana de contexto del modelo** junto a tu mensaje.
3. El modelo decide que hace falta una herramienta y emite una llamada estructurada: `run_tests` con `{ "filter": "checkout" }`.
4. El cliente del host reenvía la llamada al servidor. El servidor corre las pruebas y devuelve la salida.
5. El host inyecta la salida en la conversación como resultado de herramienta y el modelo sigue, ahora con la aserción que falla delante.

El paso 2 es el que toca tu factura, y de eso va la siguiente sección.

## Qué te cuesta en contexto

Cada herramienta que expone un servidor conectado se describe al modelo como texto: un nombre, una descripción y un esquema de sus parámetros. Ese texto está en la ventana de contexto en **cada turno**, se use la herramienta o no, porque el modelo tiene que saber qué podría llamar. Un servidor con cuarenta herramientas y descripciones largas puede añadir varios miles de tokens a cada petición antes de que escribas una palabra, y como explica el artículo sobre la ventana de contexto, la entrada se relee en cada turno.

Tres consecuencias prácticas:

- **Conecta los servidores al proyecto que los necesita, no en global.** Casi todos los hosts permiten limitar un servidor a un directorio o un espacio de trabajo. Un servidor de automatización del navegador es útil cuando depuras una web y puro lastre cuando escribes una CLI.
- **Prefiere servidores con pocas herramientas bien nombradas.** Diez herramientas precisas cuestan menos que cincuenta genéricas y, en la práctica, el modelo acierta más al elegir.
- **Vigila también el tamaño de los resultados.** Una herramienta que devuelve un log entero o una consulta de 2.000 filas mete todo eso en la ventana. Los buenos servidores paginan o resumen; si el tuyo no, pídele al agente solo las líneas que fallan.

Si miras el medidor de tu plan mientras trabajas, lo ves directamente: el mismo prompt en un proyecto con seis servidores conectados y en uno sin ninguno no cuesta lo mismo.

## Qué comprobar antes de instalar un servidor

MCP avanza rápido y el trabajo de seguridad va detrás. Un análisis de investigadores de seguridad de 2025 listó problemas abiertos como la inyección de prompts a través de resultados de herramientas y las *herramientas envenenadas*: un servidor malicioso cuyas descripciones de herramientas indican al modelo que saque datos por otra herramienta conectada. El protocolo en sí no verifica lo que un servidor dice de sí mismo.

Así que trata un servidor como cualquier dependencia a la que das acceso a tu máquina:

- **Sabe quién lo publica.** Prefiere el servidor oficial de un servicio (el de GitHub, el de Sentry, el de Figma) o las implementaciones de referencia que mantiene el proyecto, antes que un paquete desconocido que envuelve la misma API.
- **Lee lo que puede hacer.** Su lista de herramientas es su lista de permisos. Un servidor de base de datos "de solo lectura" no debería tener ninguna herramienta que escriba.
- **Cuida las credenciales.** Un servidor local suele correr con los derechos de tu usuario y con los tokens que le pases en su configuración. Dale un token limitado a lo que necesita.
- **Deja las confirmaciones puestas.** Los hosts preguntan antes de ejecutar una herramienta por algo. Quitar las aprobaciones a un servidor que instalaste hace diez minutos es como una mala descripción se convierte en una mala acción.

## Dónde te deja esto

MCP es la razón de que un agente de código en 2026 haga más que editar archivos: es como llega a tu base de datos, tu navegador, tu gestor de incidencias y tu herramienta de diseño por un solo enchufe estándar. El coste se paga en contexto en cada turno, y el riesgo es el mismo que el de cualquier código que corras con tus propios permisos. Conecta lo que el proyecto necesita, lee la lista de herramientas y mantén las aprobaciones. Otros artículos de la sección Herramientas miran qué servidores se ganan el sitio para programar y cuánto contexto se lleva cada uno de verdad.
